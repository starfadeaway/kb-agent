## 一、C 类（编造引用）的生成后校验

新增 `backend/app/agent/citation_audit.py`。判据是**工具层已落地的证据**
（本轮真正取到正文的页面），不是模型的自我陈述 —— 让模型自查有没有编引用
不可靠，它会同样流畅地为编造的页面名背书。

分两档，因为误报率完全不同：

- **L1 页面级 → 剥掉引用并计数。零误报。** 引用的页面不在本轮取到正文的页面里，
  用户点开必然是死链。
- **L2 数值级 → 只记录，绝不改文本。** 模型可能写出推导值
  （1000 攻击力 ×12% = 120，页面正文只有「12%」），
  当成幻觉削掉比留着更糟。校验器的价值取决于它不冤枉多少好答案。

三个刻意的设计决定：

1. **三态而非两态**：`checked=False` 表示本轮压根没法校验（检索全挂，
   或工具输出格式变了导致解析失败）。此时**一个引用都不剥** ——
   把「判据缺失」当成「模型大面积撒谎」，会把一次纯粹的**基础设施故障**
   削成满身弹孔的答案。这条与 `SearchGuard.observe` 的兜底同源：
   判据失效时宁可不动。同理 `checked=False` 时 `ok` 为 `False`，
   把「没法判断」报成「没问题」同样危险。
2. **流式不重写**：token 已逐片推给用户，再改 `state.answer` 会让
   「屏幕上写的」和「落库/导出的」变成两段文字，比留着编造引用更难排查。
   流式只记录，结果进 done 事件；非流式整段返回，剥除安全。
3. **越界拒答不跑**：没调过工具、正文也没引用，硬跑只会得到全假阳性。

接线：`_collect_refs` 顺手收集「页面 → 正文」，答案定型后校验。
覆盖 `_run_once` / `_finalize` / `_run_stream` 三个出口，
`AgentState` 加 `retrieved_pages` + `citation_audit`，
`/api/chat` 响应与 SSE done 事件都带上。

守卫 49 条：`test_citation_audit.py`（34，纯函数）+
`test_citation_audit_wiring.py`（15，AST 接线）。
后者存在的理由：纯函数测得再好，没接进 `react.py` 就等于零，
而这正是 C 类校验此前的真实状态 —— 只测纯函数的套件在实现被删掉时依然全绿。
双向验证：摘掉全部调用点 → 7 条接线守卫报红。

## 二、故障注入测试

新增 `backend/tests/test_fault_injection.py`（23 条）。
FakeLLM + 替换 `react` 命名空间里的 `call_tool`，不打网络/索引/token。

注入的故障：工具抛异常、工具超时、基础设施失败前缀、空结果、低分命中、
重复查询、模型调用失败、熔断后的强制收尾、流式路径下的同类故障。

**双向验证**：把 `SearchGuard.observe` 里「基础设施失败计入 miss」退回成
历史缺陷（失败落到兜底把 misses 清零），`test_连续基础设施失败触发熔断并强制收尾`
与 `test_熔断后唯一查询数不再增长` 立刻报红。这是实跑出来的，不是推测。

每组测试末尾都断言**消息链完整**（tool_call 与 tool 消息一一配对）——
FakeLLM 不校验消息链，一旦配对被 `continue`/`break` 打断，
真实 API 直接 400 而本地测试照样绿。
