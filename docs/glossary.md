# 专有名词释义

每个词分三块：**这是什么 / 在本项目里用在哪（带文件行号）/ 实测数字是多少**。

按「读代码时会遇到的顺序」排列，不是按字母。

---

## 检索层

### RAG（Retrieval-Augmented Generation，检索增强生成）

**是什么**：先从知识库检索相关资料，再把资料塞进 prompt 让模型基于它回答。
解决的问题是通用大模型的**知识截止**和**幻觉** —— 模型不知道 2024 年之后
新出的游戏道具，更容易凭训练数据编一个看起来很像的答案。

**用在哪**：不是某一个文件，而是 `retrieval/hybrid.py` 的检索链
+ `agent/tools.py` 里 `search_kb` 工具的返回体。完整路径见 `ARCHITECTURE.md` 第三节。

**本项目的实测**（`EVALUATION.md` 实验 C）：
无工具时 judge 2.50/5.00，上了完整工具链 5.00/5.00。

---

### 分块（Chunking）

**是什么**：把一篇长文档切成若干小段，每段单独存成一条检索单元。

**为什么必须切**：整页存成一条的话，检索命中了也只能返回整页，
模型不知道命中的是哪一段，而且长文本的向量语义会被稀释。

**用在哪**：`ingest/chunker.py`。策略是先按标题切逻辑段 → 再按句边界贪心打包
→ overlap 以整句回退（按字符硬切会把句子劈成两半，半句话对两个检索模型都是噪声）。

**用在哪（配置）**：`core/config.py` 的 `chunk_size` / `chunk_overlap`。

**实测**：chunk_size 500 → 3932 chunk；800 → 2808；1200 → 2238
（2026-10-13 补抓角色页后 sr 的实测值；补抓前对应 2306 / 1700 / 1407）。
chunk_size=1200 时 A3 指标从 0.966 掉到 0.931（详见实验 B，该结论基于补抓前的语料）。

---

### Embedding（向量化）

**是什么**：把一段文字压缩成一个固定长度的数字数组（向量），
语义相近的文字，向量距离也近。

**用在哪**：`llm/client.py` 的 `embed()`。索引时对每个 chunk 算一次，
查询时对问题算一次，然后比余弦相似度。

**本项目**：`BAAI/bge-m3`，1024 维。

**实测**：查询时远程调用 147ms，**已加 LRU 缓存**，重复 query 直接命中。

**坑**：不同模型的 token 上限差别很大。实测 `bge-large-zh-v1.5`
连 batch=1 都过不了（512 token 上限），而 `bge-m3` 在 batch=32 下仍然安全。

---

### 双侧归一化（双侧 L2 归一化）

**是什么**：把索引里的向量和查询向量都除以各自的模长，变成单位长度。

**为什么必须**：不归一化的话，不同长度的向量会在余弦相似度里
互相干扰 —— 一个范数大的文档天生更容易"看起来相关"。

**用在哪**：`llm/client.py` 的 `l2_normalize()`，`embed()` 默认 `normalize=True`。

---

### BM25

**是什么**：经典的相关度排序算法（TF-IDF 的改进版）。
按「词在这篇文档里出现得多不多」×「这个词在整个语料里稀不稀有」打分。

**用在哪**：`retrieval/hybrid.py` 的 `BM25Index` + `tokenize()`。
中文用 jieba 切词，再补一层中文 2-gram 兜底。

**为什么在本项目不可或缺**：星铁的「位面饰品」「行迹」「命途」
是低频专名，词面匹配比语义相似度更稳。实测纯 BM25 的 recall@3
是 0.897，而纯向量只有 0.828 且**不随 top_k 增长**。

---

### 中文 2-gram

**是什么**：把中文串切成相邻两字的组合再当词用。
「位面饰品」→ 位面 / 面饰 / 饰品。

**用在哪**：`retrieval/hybrid.py` 的 `tokenize()`。

**为什么加**：jieba 切词后专名仍可能整词未命中，补一层字符 bigram
能改善召回，且不引入新依赖（不装分词器）。

**实测**：去掉页面标题后 BM25 的 MRR 从 0.851 掉到 0.753（−9.8pt，
配对检验 p=0.0074 显著）—— 标题里的词本来就在帮词面匹配。

---

### RRF（Reciprocal Rank Fusion，倒数排名融合）

**是什么**：把多路检索结果的排名合并成一个分数：

```
score = Σ 1/(k + rank)     k 默认 60
```

**为什么用排名不用分数**：BM25 分数是无界正数，余弦相似度在 [-1,1]，
Cross-Encoder 的相关度又是另一套刻度。三者直接加权相加会被分数分布带偏。
RRF 只看名次，没有量纲问题。

**用在哪**：`retrieval/hybrid.py` 的 `_fuse()`。

**实测**：融合的增益在**排序质量**而非召回上限 ——
k=3/k=5 时 recall 和纯 BM25 完全持平（0.897 / 0.931），
但 MRR 分别 +2.3pt。所以 **RRF 是重排器，不是扩容器。**

---

### 重排（Rerank / Cross-Encoder）

**是什么**：把召回后的少量候选，逐条和问题拼在一起送进模型重新打分排序。

**用在哪**：`retrieval/hybrid.py:280` 的 `_rerank()` → `llm/client.py:174` 的 `rerank()`。

**本项目**：`BAAI/bge-reranker-v2-m3`。

**实测**：recall@3 从 0.897 → **0.966**，MRR +9.2pt。
代价是延迟 221ms → 567ms，占检索耗时的 94%。

📄 **完整说明见 `docs/rerank.md`** —— 有一篇专门文档讲这个。

---

### ANN（近似最近邻）

**是什么**：用索引结构快速找"大概最近"的向量，牺牲一点精度换速度。

**本项目为什么关掉**：`VECTOR_ANN=false`。LanceDB 0.40 的
`create_index(metric="cosine")` 已废弃，它建的是 IVF-PQ 近似索引，
会把向量量化。实测同一句查询，暴力扫描和近似索引的 top-3 第三名不同。

**评测里悄悄改变排名不可接受** —— 指标差异就无法归因到检索策略本身。
sr 生产索引 3932 chunk 暴力扫描仍是毫秒级，本来就不需要 ANN。

---

## 向量库层

### LanceDB

**是什么**：嵌入式向量数据库（不需要起独立服务）。

**用在哪**：`store/lance_store.py`。默认后端，由 `.env` 的 `VECTOR_BACKEND` 控制。

**为什么选它**：本机 Windows + Python 3.13。chromadb 1.5.9 写入后
磁盘只生成 `index_metadata.pickle`，HNSW 段目录不落盘，
换进程必然报 `Error loading hnsw index`。

---

### NumPy 精确索引（fallback）

**是什么**：把向量存成 `.npy`，查询时矩阵乘算余弦。

**用在哪**：`store/vector_store.py`，`VECTOR_BACKEND=numpy` 时启用。

**实测**：与 LanceDB 逐 case 对照 28 组，27 组排名完全一致。

---

### 分数还原：`cos = 1 - d/2`

**是什么**：LanceDB 返回的是**平方 L2 距离** d，不是余弦相似度。
换算：`cos = 1 - d/2`。

**实测校验**：cos=0.6978 ⇒ d = 2 − 2×0.6978 = 0.6044，
与 LanceDB 返回的 `_distance` 完全吻合。

---

## 存储层

### 关系库（MySQL 8.4.5）

**用在哪**：`store/db.py` + `store/models.py`，9 张表。

**存什么**：页面元数据、infobox 结构化数值（`facts`）、Agent 运行轨迹
（`runs` / `tool_calls`）、会话、评测结果。

**分工原则**：**数值走 SQL 精确查询，语义走向量。**

**为什么不用 MySQL 向量**：社区版 8.4.5 没有 `VECTOR_DISTANCE()` 函数。

---

### infobox

**是什么**：wiki 页面上的结构化信息框，星铁 wiki 里几乎所有内容都在里面。
光锥页的 `{{光锥图鉴}}` 模板有 54 个具名参数。

**为什么要展平**：见下一条。

---

### 模板展平

**是什么**：把 `{{模板|键=值}}` 转成 `字段：值` 的纯文本，**而不是删掉**。

**用在哪**：`ingest/template_parser.py`。

**踩过的最大一个坑**：早期实现是"删掉所有模板"，把 969 字的 wikitext
洗成 20 字 —— 页面抓到了，索引里等于什么都没存。
修成展平后，同一批 40 页从 9 chunk 变成 78 chunk。

## Agent 层

### ReAct

**是什么**：Reason + Act 的循环 —— 让模型交替进行「推理」和「调用工具」，
直到它认为信息足够、给出最终答案。

**用在哪**：`agent/react.py`（约 380 行，手写不依赖 LangGraph）。

**为什么不用框架**：JD 明确写了"关注上下文、工具调度、运行状态、异常处理
和效果评测，而不只是完成模型 API 调用"。手写能把这些点全部暴露出来。

---

### 工具 schema

**是什么**：告诉模型有哪些工具可用、每个工具要什么参数的 JSON 结构。

**用在哪**：`agent/tools.py` 的 `@tool` 装饰器。

**踩过的坑**：少一层 `{"type": "function"}` 包装，DeepSeek 直接
400 `Invalid schema for function`。

---

### SearchGuard（熔断）

**是什么**：给检索类工具上的两道保险 —— 查询指纹去重 + 连续低置信度强制收尾。

**用在哪**：`agent/react.py` 的 `SearchGuard`。

**为什么需要**：知识库里没有的问题，Agent 会一直检索到顶满步数。
实测 7 步 / 30317 tokens 才承认查不到 —— 行为没错，成本完全失控。
修复后 4 步 / 6514 tokens（**−78%**）。

**关键设计**：`search_kb` 返回体第一行是机器可读状态
（`status=ok hits=3 top_score=0.912 ...`），Agent 靠它判断
「这次到底找到没有」。没有这层，模型会把「召回了但都不相关」
当成「再搜一次说不定有」。

---

### 四道安全阀

| 阀 | 防什么 | 配置项 |
|---|---|---|
| 最大步数 | 工具调用死循环 | `AGENT_MAX_STEPS` |
| token 预算 | 上下文/费用失控 | `AGENT_TOKEN_BUDGET` |
| 墙钟超时 | 慢工具拖死整条链 | `AGENT_WALL_TIMEOUT` |
| 单工具超时 | 单个工具卡住 | `TOOL_TIMEOUT` |

---

### SSE（Server-Sent Events）

**是什么**：服务端单向流式推送。用于打字机效果。

**用在哪**：`main.py` 的 `/api/chat/stream` + `react.py` 的 `_run_stream`。

**实测价值**：非流式端到端 4716ms 用户全程干等；
流式首字 **721ms**。**感知延迟 −85%，总耗时几乎不变。**

---

### TTFT（Time To First Token，首 token 延迟）

**是什么**：从发出请求到收到第一个 token 的时间 —— 这才是用户感知的「延迟」，
不是总耗时。

**用在哪**：`scripts/probe_stream_latency.py` 的测量指标。

---

### KV Cache（上下文缓存）

**是什么**：把已经算过的前缀 KV 张量缓存起来，下次同前缀请求直接复用。

**本项目状态**：DeepSeek **自动生效，零配置**，`usage.prompt_cache_hit_tokens`
可见，命中率 80%+。

**但它省的是费用不是延迟** —— 实测首 token 延迟稳定在 100–350ms，
总耗时由生成 token 数决定。要降延迟靠流式。

---

## 评测层

### recall@k

**是什么**：gold 结果里有多大比例出现在 top-k。
多 gold 时用比例而非 0/1。

**本项目口径**：gold 标的是**页面**，判定时把 chunk 命中折算成页面排名
（`metrics.page_ranking`）。

**为什么标页面不标 chunk_id**：chunk 边界随 chunk_size 变化，
绑死 chunk_id 会让「重建索引」等价于「评测集失效」。

---

### MRR（Mean Reciprocal Rank，平均倒数排名）

**是什么**：第一个正确结果排名的倒数，再对所有查询取平均。

**在本项目的作用**：衡量排序质量。它比 recall 更敏感 ——
recall@5 持平的两个配置，MRR 可能差很多。

---

### NDCG（归一化折损累计增益）

**是什么**：带位置折损的召回 —— 排第 1 得 1 分，排第 5 只得 0.39 分。

**为什么同时要 recall 和 NDCG**：recall 只看「在不在」，NDCG 看「在多前面」。

---

### 配对 t 检验

**是什么**：比较两个配置在同一批题上的差异，**先消掉 case 难度这个方差源**。

**为什么必须做**：消融实验里所有配置跑的是同一批题，而 case 难度差异极大
（结构化字段题几乎必中，语义题经常不中）。非配对比较会把
「这批题恰好简单」误判成「这个配置更好」。

**局限**：本机没 scipy，用正态近似算 p 值，n<20 时标注不可靠。

---

### Cohen's d（效应量）

**是什么**：差异的实际大小（均值差 / 合并标准差）。

**为什么统计显著还要看它**：n 大的时候 0.01 的差异也能显著，
但那可能没有实际意义。

**本项目实例**：实验 B 的 embed_mode 检验 p=0.0074（显著）
但 d 只有 −0.312（小效应）—— 说明差异真实但不大。

---

### LLM-as-a-Judge

**是什么**：用 LLM 给答案打分。

**三条不可妥协的规则**（`eval/judge.py`）：

1. **Judge 必须与被测模型不同源** —— 严禁 DeepSeek 答、DeepSeek 评
   （self-preference bias 会让它系统性偏好自己的表达风格）。本项目用 Qwen。
2. **成对比较必须交换位置跑两遍** —— LLM 对「先出现的答案」有稳定偏好。
3. **给出上下文再问忠实度** —— 不给证据就问「有幻觉吗」，
   Judge 只能凭常识猜，测的是它自己的知识。

---

### 单变量阶梯消融

**是什么**：每次只打开一个开关，A→B→C 逐步加能力。

**为什么**：差值才可归因。多变量对比会得到「B 比 A 好」，
但不知道是哪个组件起的作用。

**本项目**：实验 A（A0/A1/A2/A3）、B（B0–B3）、C（C0/C1/C2）、D。

---

### 隐藏变量

**是什么**：会影响结果、但你没意识到的因素。

**本项目踩到的三个**：

1. rerank 模型是 bge 专用 → 换 embedding 模型做对比时必须关掉重排
2. 向量范数分布不同 → 换模型时必须双侧归一化
3. 评测集里纯语义题太少 → 融合检索的优势测不出来（10 条 vs 32 条结论符号相反）

## 语料层

### MediaWiki API / Action API

**是什么**：wiki 的标准接口。本项目通过 biligame 的 API 抓取。

**用在哪**：`ingest/wiki_client.py`，三个接口：
`list_category_pages`（枚举）、`get_pages`（批量取，一次 10 页）、`fetch_page_meta`（取修订号）。

---

### wikitext

**是什么**：wiki 页面的源代码，不是渲染后的文本。

**为什么要处理**：wikitext 里全是 `{{模板}}` 和 `[[链接]]`，直接扔给模型是噪音。

---

### EdgeOne 567

**是什么**：biligame 前面的腾讯云防护返回的**限流挑战页**状态码。

**关键**：它**不是 404**。看到 567 就断言「这个页面不存在」是错的。

**对策优先级**：批量取页（一次 10 页）> 拉长间隔 > 退避重试。
实测 518 页 0 次拦截。

---

### 分类命名空间「分类:」

**是什么**：MediaWiki 里分类页面的前缀，中文站是「分类:」不是 `Category:`。

**踩过的坑**：只写死一种前缀，`list_category_pages` 会静默返回空列表 ——
看起来像「这个分类没内容」，实际是路径错了。
另外 MediaWiki 会把错误放在 `query.errors` 里而 HTTP 仍是 200。

---

### 版本感知 chunk

**是什么**：每个 chunk 带 `last_revision`（修订号）和 `last_revision_ts`。

**用在哪**：`ingest/pipeline.py` 写入，`retrieval/hybrid.py` 可按时间戳过滤。

**为什么**：游戏每次版本更新都会改数据。把 wiki 当静态语料，
就会出现「检索到 1.0 版本的旧数值」。
