# 五个实验在做什么，为什么要做

> 这份文档回答两个问题：**每个实验想证明什么**、**结果里每一列是什么意思**。
> 具体数字看 [`../EVALUATION.md`](../EVALUATION.md)，原始 JSON 在 `data/eval/exp_*.json`。
>
> 写这份文档的起因：隔了一段时间回看 `exp_a/b/c/d/e` 这些名字，
> 已经想不起来当初为什么要有 B3 那一步、为什么 C 要分三级。
> 于是把「问题 → 实验 → 结论」这条链固定下来。

---

## 零、先说纪律：这五个实验的共同约束

它们**不是五个独立课题，是一条递进的链**。每一个都比前一个更贵、更接近真实使用：

```
A 检索策略    —— 知识怎么找        （便宜，纯检索，无 LLM 生成）
B 分块策略    —— 知识怎么切        （更便宜，但要重建索引）
C 工具开放    —— Agent 能做什么    （贵，要生成 + Judge）
D 嵌入模型    —— 换向量模型值不值  （很贵，要重建索引 + 全量重新嵌入）
E Chat 基座   —— 换大脑值不值      （最贵，含跨厂商协议适配）
```

排在前面的是「先把地基调对，再谈上层」。B 在 C 之前，是因为分块没定就没必要去测 Agent；
D 排在 C 之后，是因为换了向量模型却没验证检索质量，是本末倒置。

### 单变量纪律（最容易翻车的地方）

每个实验**只允许一个东西变**，其余全部冻结。之所以要这么较真：

- 一旦同时变两个，任何差异都无法归因。你会看到"A 比 B 好 8 个点"，
  却说不清是分块的功劳还是嵌入模型的功劳。
- 别人的追问也只有在单变量下才答得上来。面试里最常见的致命问题是
  "你怎么知道是这个原因不是那个"，答案只能是"我只改了这一个"。

各实验的冻结清单写在对应脚本头部（如 `exp_e.py` 顶部列了完整冻结项），
改任何一个实验前先读那段注释。

### 为什么 B 要绕一圈（B0→B1→B2→B3）

因为"改分块"和"改 embed_mode"是两个独立的维度，混在一起就分不清谁的锅：

| 步骤 | chunk_size | embed_mode | 相对上一步改了什么 |
|---|---|---|---|
| B0 | 500 | title | 基准 |
| B1 | 800 | title | 只改 chunk_size |
| B2 | 1200 | title | 只改 chunk_size（继续阶梯） |
| B3 | 500 | **text** | 退回基准分块，**只**改 embed_mode |

B1/B2 是一维阶梯（分块从小到大），B3 先把 chunk_size 拨回基准再动另一个维度。
如果 B3 直接在 1200 的基础上改 embed_mode，就同时变了两个东西。

### 为什么 C 要分三级而不是只比"有 RAG vs 没 RAG"

三级分别回答不同的问题：

- **C0（无工具）**：纯靠模型训练数据答题。这是基线，也是"通用大模型在垂直领域会怎样"的答案。
- **C1（只给 search_kb）**：能查知识库。验证"检索注入"本身有没有用。
- **C2（给全套工具）**：再加 `get_page` / `calculator` / `list_games`。验证"多工具"是否带来额外收益。

只做首尾对比（C0 vs C2）无法回答"收益来自检索还是来自工具数量"。
注意 C0 不走 ReAct 循环（直接单轮问答），否则模型收不到工具声明会反复尝试调用——
这是实现细节，但它保证了 C0 的耗时和 C1/C2 不是同一个量级。

## 一、实验 A：检索策略阶梯消融

**要回答的问题**：把 BM25、向量、融合、重排一个一个打开，性能怎么变？值不值得？

**唯一变量**：检索链路开到第几级。

| label | 链路 | 含义 |
|---|---|---|
| A0 | 只用 BM25 | 纯词面匹配 |
| A1 | 只用向量 | 纯语义匹配 |
| A2 | BM25 + 向量（RRF 融合） | 两路取长补短 |
| A3 | A2 + 交叉编码重排 | 完整链路 |

**为什么不跑"只重排"**：重排的输入是融合后的候选，单独跑没有意义。

**复现**：
```powershell
.\.venv\Scripts\python.exe backend\scripts\run_eval.py --experiment A --game sr --top-k 3
```

## 二、实验 B：分块与索引文本

**要回答的问题**：一个页面切成多大块最优？送进 embedding 的文本要不要带页面标题？

**为什么这个实验值得单独做**：游戏 wiki 里有大量"位面饰品/光锥/圣遗物"这类结构化表格。
切太大，一块里混了好几个实体，语义被稀释；切太小，脱离上下文。
而 `embed_mode` 是另一个常被忽略的维度——把标题拼进索引文本，
相当于给每个块加了个"我在哪一页"的锚点。

**索引规模怎么看**：`chunk_size=500 → 2306 chunk`、`800 → 1700`、`1200 → 1407`。
指标要在**同一批题**上比，不同 chunk 数的索引天然召回的东西不一样。

**复现**：
```powershell
.\.venv\Scripts\python.exe backend\scripts\exp_b.py --game sr --steps B0,B1,B2,B3 --top-k 3
# B0 是基准索引，不重建，只跑评测：
.\.venv\Scripts\python.exe backend\scripts\exp_b.py --game sr --steps B0 --top-k 3 --skip-rebuild
```

## 三、实验 C：工具开放程度

**要回答的问题**：给 Agent 挂知识库检索到底有没有用？多给几个工具有没有额外收益？

**与 A/B 的本质区别**：A、B 只测"能不能找对"，C 测"**能不能答对**"——
包含生成环节，所以需要 Judge 打分，也就贵得多。

**结果结构**：`exp_C.json` 里每一档有 `judge_score` / `correctness` /
`faithfulness` / `completeness` 四项，以及 `steps` / `tok`。

**复现**：
```powershell
.\.venv\Scripts\python.exe backend\scripts\exp_c.py --labels C0,C1,C2
```

## 四、实验 D：换嵌入模型

**要回答的问题**：换向量嵌入模型，效果和成本怎么变？

**实现细节**：每个模型写进**独立的 variant**（独立 collection），
否则两套维度的向量会写进同一个索引，查询侧维度不匹配。
实测 BAAI/bge-m3 与 Qwen/Qwen3-Embedding-0.6B 都是 1024 维。

**默认不跑 A3（重排）**：重排器 `BAAI/bge-reranker-v2-m3` 是配合 bge 嵌入训练的，
换嵌入模型时仍开着它等于引入隐藏变量（候选集构成变了，却仍用旧的交叉编码器打分）。

**复现**：
```powershell
.\.venv\Scripts\python.exe backend\scripts\exp_d.py --models BAAI/bge-m3,Qwen/Qwen3-Embedding-0.6B --top-k 3
```

## 五、实验 E：换 Chat 基座

**要回答的问题**：换聊天模型（大模型应用工程师真正会动的那一层）值不值？

冻结清单：temperature=0、同一套 tools schema、系统提示不改一个字、
同一批 15 条评测题、同一个独立 Judge 基座。

**为什么要做两处适配**（MiniMax）：
1. 它会输出 `<think>` 标签，直接塞进 assistant content 会污染后续轮次消息链 —— 剥掉；
2. 工具调用协议与 OpenAI 不完全一致 —— 把 content 里的 JSON 解析回标准 `tool_calls` 兜底。

> E 是**唯一**测"换大脑"的实验。如果只做一个跨厂商对比，选它。

**结论（2026-10-13 重跑，详见 EVALUATION.md）**：

| | E1 deepseek-chat | E2 MiniMax-M2.5 |
|---|---|---|
| judge 分 | 4.5714 (n=14) | 4.0000 (n=15) |
| 延迟 | 3696ms | 15231ms |

配对检验（n=14）：judge 分 Δ=−0.6071、**p=0.1667 不显著**；延迟 **4.08×、p=0.0011 显著**。
所以结论是「**质量未达显著差异、延迟差 4 倍**」，**不是**「DeepSeek 更强」。

两个基座的**失败模式互补**，这是逐 case 才看得出来的：
MiniMax 在假前提题上更诚实（宁可搜 8 轮、烧 5.5 万 token 才敢说"库里没有"），
但会出现「检索到了却误判成未收录」的假阴性、以及 `steps=0` 不调工具直接复述系统提示；
DeepSeek 快 4 倍、省一半 token，短板是幻觉（会提到库里不存在的「不老者的仙舟」）。

> ⚠️ 重跑时 `sr-008` 被剔除：它是 **Judge 侧 `APITimeoutError`**，0 分纯属评测链路抖动，
> 而它的答案实为一段正常的攻击力计算推导。剔除前后 Δ 从 +0.27 变成 +0.61。
> 注意这次剔除的是 E1 而非上一版的 E2 —— **故障落在哪一档是随机的**，
> 所以剔除规则必须落在通用的 `is_kept()` 上，不能针对某档写。

**复现**：
```powershell
# 两档一起跑最稳（约 50 分钟）；超过 60 分钟请分两次跑，产物用 --out 分别指定
.\.venv\Scripts\python.exe backend\scripts\exp_e.py --labels E1,E2 --concurrency 2 --out exp_E.json
```

## 六、指标词典

检索类（A/B/D 用）与生成类（C/E 用）分开看，混用会得出荒谬结论。

### 检索指标

| 指标 | 含义 | 怎么读 |
|---|---|---|
| `page_hit` | top-k 里出现了**任意一个** gold 页面即算命中 | 最宽松，只看"有没有捞到" |
| `recall@k` | 命中的 gold 页面数 / gold 页面总数 | 多 gold 题时比 page_hit 严格 |
| `mrr` | 首个正确结果排名的倒数，平均 | **看排序质量**，不只看有没有捞到 |
| `ndcg` | 考虑多级相关性与位置的指标 | 最严格，同时罚"没找到"和"排太后" |
| `avg_latency_ms` | 单条平均耗时 | **只在同批次内可比**，见下方警告 |

`page_hit` 和 `mrr` 经常给出不同答案：如果 A3 和 A2 的 page_hit 都是 0.966，
但 mrr 从 0.874 升到 0.966，说明重排的价值是**把对的排到前面**，不是"多找到了"。
这正是 A3 存在的意义。

### 生成指标

| 指标 | 含义 |
|---|---|
| `judge_score` | Judge 给的总分，是 C/E 的主指标 |
| `correctness` | 事实是否正确 |
| `faithfulness` | 是否忠于检索到的材料（**防幻觉**） |
| `completeness` | 是否答全了 gold 的要点 |
| `steps` | ReAct 循环走了几步，越少越好（每步都是钱和延迟） |
| `tok` | prompt token 消耗，直接对应成本 |

### 统计量

| 统计量 | 含义 | 注意 |
|---|---|---|
| `p` | 显著性 | **本项目用正态近似，不是 t 分布**，详见 EVALUATION.md 开头的口径披露 |
| `Cohen's d` | 效应量 | 统计显著 ≠ 实际有意义，d 太小不该写进简历 |
| `Δ` | 配对均值差 | **方向约定：后 − 前，正数 = 这次改进是正收益** |

## 七、四个会把人带沟里的坑

这些不是假设，是本项目实际踩过并修掉的。

### 1. `Δ` 的符号方向

`paired_test(a, b)` 算的是 `a - b`，符号完全由调用方传参顺序决定。
项目里曾把 `(基线, 改进档)` 传进去，于是 A2→A3 打出 `Δ = −0.092`，
而 A3 的 MRR 明明高 9.2 个点——**数字算得对，符号读起来是反的**，
照抄进简历就会写成「A3 比 A2 下降」。

现在约定统一为**后 − 前，改进为正**，由 `test_paired_direction.py` 守住。

### 2. 延迟数字必须带口径

同一个"rerank 裁剪省了多少"，在两种缓存状态下能得出差 7 倍的结论：

- **冷缓存**（每个 label 前 `clear_caches()`）：−14.8%
- **热缓存**（两组都预热过）：−2.0%

两者都对，差的是缓存状态。裁剪省的是"那次真的调用远程 rerank"的钱和时间；
一旦命中缓存，裁不裁几乎没差别。**引用延迟数字必须带口径。**

### 3. 延迟的顺序效应

只预热第一条 query、剩余 14 条冷启动全落在先跑的那一组时，
同一份代码隔一分钟重跑，中位数能从 +18.4% 翻到 −31.2%。
这不是抖动，是"谁先跑"混进了变量。**对照实验前必须让两组处于同一缓存状态。**

### 4. 样本量与措辞

n=14~15 时不要把 p 的具体位数写进简历，写「p<0.001（正态近似）」并注明口径更诚实。
同理，"p50 从 A 涨到 B"这种几十毫秒的差异，在远程 API 抖动面前大概率是噪声——
**结论要站稳，依赖的是量级差异，不是那几十毫秒**。

## 八、跑之前该知道的事

- **重建索引会消耗 embedding 配额**。改分块/换模型后必须重建，
  `rebuild_index.py --help` 确认参数与目标 variant 一致，别把「补漏」变成第二个变量。
- **实验跑完记得 `--no-persist` 的语义**：不加才落 MySQL。
- **改完代码要重跑全部实验**，否则新旧数字混在一张表里对不上。
  每个实验脚本都会读磁盘上的 `exp_*.json` 汇总，改了 A 却没重跑 B，
  汇总表里就会同时出现两个时期的数据。
