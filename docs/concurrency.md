# 并发：Agent 能不能多开，同时跑会怎样

> 本文所有数字来自 `scripts/bench_concurrency.py` 的实测，命令可复现：
> ```bash
> python scripts/bench_concurrency.py --mode retrieve --levels 1,2,4,8
> ```
> 原始结果（含每条 query 的逐次延迟）落盘到 `data/eval/bench_concurrency_retrieve.json`，
> 带 `_meta` 出处块（脚本名 / UTC 时间 / git commit / 并发档位）。
> 压测输入取自评测集 `eval_cases` 的**真实问题**，不是 `"test"` 这种退化短串 ——
> 短串不触发 BM25 分词差异，测出来的并发能力是假的。

## 一句话结论

**能开，而且几乎不用改代码。** 这套 Agent 的瓶颈全在远程 API（rerank 449ms / embed 147ms / chat 614ms），
本地计算只占几毫秒，所以并发几乎线性地换来吞吐。真正的限制只有一条：
`CONCURRENCY_LIMIT=4`，超过就排队。

## 实测：检索路径（`/api/retrieve`，A3 全链路 BM25+向量+Rerank）

服务端 `CONCURRENCY_LIMIT=4`，每档用**互不重叠**的真实 query 切片
（否则后一档会白捡前一档的 embedding/rerank 缓存，测出"并发反而更快"的假结论）。

| 并发度 | p50 | max | 吞吐(req/s) | 吞吐倍数 |
|---|---|---|---|---|
| 1（串行基线） | 796ms | 796ms | 1.26 | 1.00x |
| 2 | 515ms | 685ms | 2.92 | 2.32x |
| 4 | 736ms | 799ms | 5.01 | 3.98x |
| 8 | 1103ms | 1382ms | 5.78 | 4.60x |

两个要点：

1. **并发 4 时吞吐涨到 3.98 倍，而单请求 p50 基本没变（796ms → 736ms）。**
   说明本地部分几乎不争抢资源 —— 等待时间全花在等远程 API 上，
   而那些等待本来就是可以重叠的。

   > ⚠️ **别把 736 当成"变快了"**。它是**低于** 796 的，也就是 p50 不升反降，
   > 这种反向的微小差异在远程 API 的抖动面前大概率是噪声，不是"并发能加速"。
   > 每档只有 5 条 query，样本量本来就不足以分辨这个量级的差别。
   > 结论要站稳，依赖的是**吞吐 3.98 倍**这个量级差异，不是这 60ms。
   > 逐次延迟在 `data/eval/bench_concurrency_retrieve.json` 的 `per_request_ms` 里，
   > 判断抖动大小看方差，不要只看 p50。

2. **并发 8 时吞吐只到 4.60 倍、p50 涨到 1103ms**，因为多出的 4 个请求
   在信号量上排队。这是设计内的背压，不是 bug。

> 这张表是**重建 sr 索引之后**（2293 → 2306 chunk）重跑的，出处块里记着
> git commit 与 UTC 时间。换语料后请重跑本表，不要沿用旧数字。

### 确定性有没有被并发破坏

同一个 query 在 1 / 2 / 4 / 8 并发下重跑，`top5 chunk_id` **逐条完全一致**
（`sr-1494-0000, sr-1494-0004, sr-4304-0000, ...`）。

这不是运气：整条检索链路没有任何依赖执行顺序的可变状态 ——
BM25 索引只读，RRF 融合按 `(rank_source, rank)` 稳定排序，
向量扫描是纯 NumPy 矩阵乘。**并发只改变"什么时候算"，不改变"算出什么"。**

### ⚠️ 生成侧**不成立** —— `temperature=0` 不等于可复现

检索侧确定性成立，**但生成侧（ReAct + LLM + Judge）完全不成立**。

`scripts/probe_concurrency_consistency.py` 复用 `exp_e.run_one` 生产路径，
同一批 15 条、同一档 E1、并发度 1 vs 2，各跑一遍后逐条对比：

| 对比项 | 一致条数 |
|---|---|
| **`answer` 原文完全相同** | **0 / 15** |
| `prompt_tokens` | 6 / 15 |
| **`judge_score`** | **9 / 15** |
| `faithfulness` | 10 / 15 |
| `steps` | 12 / 15 |
| `correctness` | 14 / 15 |

```
aggregate judge_score:  c1 = 4.6667    c2 = 4.5667
judge 分不一致的 6 条：sr-008 / sr-009 / sr-011 / sr-013 / sr-030 / sr-031
```

**没有任何一条答案完全相同。** 而 `temperature` 已经冻结为 0 ——
说明波动的来源不是采样随机性，而是浮点非确定性、缓存命中与否、
批处理组合这些**同样由并发与运行环境决定**的因素。

这条结论对本项目的影响比看上去大：

1. **生成类实验（C/E）的均值有 ±0.10 量级的运行间波动。**
   实验 E 的 E1 在本探针两次分别是 4.6667 / 4.5667，
   而正式那次是 4.5714 —— 三次跑出三个值。
2. **反过来它加强了实验 E 的结论**：E1 vs E2 的差是 0.61，
   是运行间噪声（~0.10）的数倍，但 p=0.1667 仍未达显著，
   所以「质量差异不显著」这个判断是稳的。
3. **面试时正确的说法**是「检索链路可复现、生成链路不可复现，我量化了两者的差异」，
   而**不是**「我的实验完全确定性可复现」—— 后者一说就会被追问，
   而本项目已有实测数据把它证伪了。

### 并发对生成侧没有加速（反而更慢）

| 并发度 | 15 条总用时 |
|---|---|
| 1（串行） | **751.3s** |
| 2 | **843.0s** |

并发 2 比串行**更慢**。原因与实验 C 的发现一致：
Judge（SiliconFlow Qwen3-8B）单次就要 28.5s，是整条生成链的瓶颈，
把它并发出去并不会缩短墙钟时间，反而带来排队与外部 API 的并发争抢。

> 因此**评测脚本的 `--concurrency` 只应按「外部 API 的并发额度」来定，
> 不是越高越快**。检索侧的吞吐表（并发 4 → 3.98x）不能外推到生成侧。

## 共享状态盘点：哪些东西是多个请求共用的

| 组件 | 是否共享 | 并发安全性 | 说明 |
|---|---|---|---|
| `HybridRetriever` | 是（进程级单例） | ✅ 安全 | BM25/语料缓存建好后只读；`_load_corpus`/`_get_bm25` 是同步且内部无 `await`，在 asyncio 下无法被交错执行 |
| `Collection`（向量库） | 是 | ✅ 写加锁、读无状态 | `upsert` 有 `threading.Lock`；`query` 是纯 NumPy 矩阵乘 |
| `LLMClient` | 是（`get_llm()` 单例） | ✅ 安全 | embedding/rerank 缓存未命中时**各算各的**，只是重复调用，结果一致（确定性函数） |
| MySQL 连接池 | 是 | ⚠️ 偏小 | `pool_size=5`，而并发上限是 4 —— 能用，但余量只有 1 |
| `_semaphore` | 是 | ✅ 设计如此 | 4 个槽位，`/chat`、`/retrieve`、`/ingest` **共用** |

> 注：`/ingest`（抓 wiki）和 `/chat` 抢的是同一个信号量。
> 所以入库时提问会排队 —— 这是好事，入库很慢且要过 WAF，不该和用户请求抢资源。

## 三个真实存在的坑（都已处理 / 已记录）

### 1. BM25 建索引会阻塞整个事件循环 —— 已修

`hybrid.py` 的 `_get_bm25()` 是**同步函数且内部没有 `await`**。
正常情况下启动预热已经建好索引，它只是一次 dict 查找。
但 `/ingest` 会调 `reset_retriever()` 清空缓存 —— 这时**下一个请求**
要现场建索引，而这一建就是 ~1.8s 的纯 CPU（jieba 分词）。

由于函数里没有 `await`，这 1.8s 里事件循环完全无法让出，
**所有并发中的请求一起停摆**，表现为"服务突然卡住"。

修法：`/ingest` 之后用 `asyncio.to_thread` 在后台重建索引
（`main.py: _warmup_after_ingest`），用户无感，也不阻塞任何人。

> 为什么不用「把 `_get_bm25` 整体丢进线程」这种更彻底的做法：
> 那会让预热线程和事件循环真正并发写同一个 dict，
> `_evict_locked()` 里的 `next(iter(dict))` 会在迭代中被另一个线程改动，
> 直接 `RuntimeError: dictionary changed size during iteration`。
> **当前的同步设计在 asyncio 下是正确的**，值得为了并发去破坏它。

### 2. 缓存未命中会重复调用远程 API —— 可接受

两条完全相同的请求同时进来，会各自调一次 embedding + rerank。
因为这两个都是**确定性函数**（同输入必同输出），结果不会错，只是多花了钱和延迟。
真实线上流量里重复 query 占比不高，不值得为它引入分布式锁。

### 3. MySQL 连接池比并发上限只多 1 —— 建议调大

`pool_size=5` vs `CONCURRENCY_LIMIT=4`。当前够用，但一旦把并发调到 8 就会开始报
`QueuePool limit ... overflow`。**要放开并发，先把 `pool_size` 一起调到 `concurrency_limit + 2`。**

## 想真的开多，可以怎么做

按代价从低到高：

1. **直接调大 `CONCURRENCY_LIMIT`（改 `.env`）** —— 检索路径已经证明能线性扩展。
   同步把 MySQL `pool_size` 调大。

2. **`--workers N` 多进程**（uvicorn）—— 能用，但**有两个坑**：
   - 每个进程各自建一份 BM25 索引。实测一份 ~几十 MB，4 个进程就是 4 倍内存。
   - LanceDB 目录被多进程并发写有风险；MySQL 那部分反而没问题（本来就是多客户端）。
   内存够、且不需要共享内存缓存时才值得。

3. **把 BM25 建索引彻底挪出事件循环** —— 需要先给 `_text_cache` / `_bm25_cache`
   加真正的 `threading.Lock`（含淘汰逻辑）。当前规模（2 个库）用不上。

## 该怎么在面试里讲这件事

不是"我的系统能并发"，而是这三句：

1. **我测过，不是猜的** —— 给并发度-延迟-吞吐表，并指出并发 4 时吞吐 3.98 倍而 p50 几乎不变，
   由此定位瓶颈在远程 I/O 而非本地计算。
2. **我验证过并发没有破坏确定性** —— 同 query 在各并发度下 top5 完全一致，
   因为链路里没有依赖执行顺序的可变状态。
3. **我知道当前的边界在哪** —— 主动说出"信号量是全局共用的、入库会占槽位、
   连接池比并发上限只多 1、多进程会让 BM25 索引内存翻 4 倍"。
   能说出边界，比能扛住压测更能说明工程经验。
