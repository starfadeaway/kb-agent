# 知识库怎么跟着游戏版本迭代

> 实测数据来源：`data/eval/probe_delta_sync.json`，
> 由 `scripts/probe_delta_sync.py` 生成，可复现。
>
> **本文最重要的一条不是"该怎么更新"，而是"我差点因为算错口径得出相反结论"。**

---

## 一、先把问题问对

版本迭代落到工程上不是"让模型重新导一次"，模型从来不参与导入。
真正的链路是确定性流水线：

```
wiki → 抓取 → 切块 → embedding → 索引 → 检索
```

问题出在**第一个环节之前**：系统不知道哪些页面变了。
所以「更新」的本质是**变更检测**，不是「重新导入」。

现状盘点（代码事实）：

| 环节 | 现状 |
|---|---|
| 断点续传 | ✅ `crawl.py:40` `load_ckpt()` 按 `done_titles` 跳过已抓 |
| 批量取页 | ✅ `titles=A\|B\|C` 一次 10 页，累计 886 页 0 拦截 |
| 残留剪枝 | ✅ `persist.py:397` 以当前语料为准删孤儿 |
| 版本过滤 | ✅ `min_revision_ts` 已在检索层生效并双向验证 |
| **内容指纹** | ✅ 已落地：`ingest/fingerprint.py`，1401 页 / 10843 chunk 覆盖率 100% |
| **增量检测** | ✅ 已落地：`ingest/delta_sync.py:123` `detect_changes()` |

> ⚠️ **这两行此前标的是 ❌。** 它们当时确实是根因：
> `load_ckpt()` 只认标题集合，于是**已抓过的页面永远不会被重新抓**；
> 名义上的"更新"实际是「删掉 checkpoint + `--fresh` 全量重来」——
> 能工作，但**没有任何机制告诉你它该不该做**。
> 本文档第三节起记的就是把这两行补上的过程与实测，所以这里按**最终状态**标 ✅。

## 二、实测一：wiki 侧的增量接口是通的

| 接口 | 判定 | 用途 |
|---|---|---|
| `list=recentchanges` | ✅ | 按时间窗口列出被改过的页面 |
| `recentchanges` + `rcstart`/`rcdir` | ✅ | 只看上次同步之后的 |
| `generator=allpages` + `rvprop=timestamp` | ✅ | 批量查修订时间，不取正文 |

三者都能穿过 EdgeOne。这一点之前是未知的 —— 早先的结论是
「只能靠拉长间隔硬扛」，后来发现批量取页（一次 10 页）才是对付 WAF 的有效手段，
所以 `recentchanges` 是否也在这条豁免路径上必须实测，不能推断。

## 三、实测二：算错口径会得出**相反**的结论

这是本文最值钱的一节。

第一版实测只统计了**全站**变更页：

```
近 7 天：2922 条变更 → 去重 1157 个页面
sr 本地收录：706 页
1157 / 706 = 163.9%
```

按这个数字，增量毫无意义 —— 一周内被改过的页面比整个库还多，
不如定期全量重抓。**但这个结论是错的。**

原因在于口径：1157 是**全站**口径，包含活动公告、版本专题、玩家投稿闲聊页，
而本项目只收录 12 个分类。真正该算的是交集：

| 口径 | 近 7 天页数 | 相对本地库 |
|---|---|---|
| 全站变更页 | 1157 | 163.9% |
| **变更页 ∩ 已收录页** | **162** | **23.0%** |

| 口径 | 页数 | 省下的抓取量 |
|---|---|---|
| 全量重抓 | 706 | — |
| 增量（只抓变更页） | 162 | **77%** |

**差了一倍多。** 全站口径会把 6 倍于实际成本的数字喂给决策。

> 交集的精确值是 **162 / 23.0%**（窗口翻完，2922 条全读到）。
> 本文早期版本写的 148 是 WAF 截断时的**下界**，已更正。
>
> 检测本身的请求量：**15 次**（recentchanges 6 次 + revision 批量 9 次）。
> 全量重抓需要 71 次（706 页 / 每批 10 页）。检测成本只与"最近变更量"有关，
> 与语料规模基本无关。


> 口径纪律：算"增量成本"时，分母必须是**你会同步的那个集合**，
> 不是"那个站上有多少页"。这两个集合的重合度决定了结论能不能翻转。

### 数据边界要说清楚

- 探针阶段（`probe_delta_sync_scope.py`）那次 7 天窗口**没翻完**，
  当时读到 1003 页 / 2500 条就吃了 567，所以那版交集 148 **只是下界**。
  后面用 `delta_sync` 重跑翻完了全部 2922 条，精确值是 **162**。
- 30 天窗口那次被 WAF 全拦，交集 0 **不可用**，
  不能读成"30 天零变更"。脚本对此会显式告警。
- WAF 实测：`rclimit=500` 翻页时，**6s 间隔打到第 3 页就吃 567**，
  退避要 15s 起（`--interval` 默认已是 15）。
- 本地收录数有两个口径：**706**（MySQL `pages` 表，进过索引的）
  与 **707**（checkpoint `done_titles` 并集，含被 `page_filter` 挡掉的 1 页模板页）。
  检测用前者，因为它要知道每页的指纹。

## 四、真正的难点不是抓，是失效

三类失效，现有机制只覆盖第一类：

| 类型 | 现象 | 现状 |
|---|---|---|
| 正文改了 | 角色倍率调整、技能描述变更 | 无检测手段 |
| 页被删/改名/合并 | 本地留下幽灵页，模型照答 | 无检测手段 |
| **同事实两版本并存** | wiki 两个页面各写一份，模型随机引用 | 完全没防 |

第三类最毒：不是答错，是**答得对但答案是旧的**。

`docs/version_staleness.md` 实测过：sr 语料 **30% 是两年多以前的内容**，
`min_revision_ts` 能把 top-5 里的陈旧页从 77.2% 清到 0。
但那是**事后过滤**，不是**更新** —— 过滤只能挡掉"你没要求看旧内容"的情况，
挡不住"用户直接问了一个 2023 年的问题"。

## 五、必须先解决的一个工程陷阱

chunk_id 形如 `sr-1494-0000`，即 `f"{page_id}-{序号}"`。

页面内容改了，**page_id 不变 → chunk_id 不变 → 旧 embedding 被当成有效数据**。

后果是系统显示"更新成功"，索引里却同时存在新旧两个版本，
而且**没有任何报错**。这比不更新更糟：不更新至少是诚实的旧数据，
混版本则是让模型在两个矛盾的事实里随机挑一个。

解法只有两条：

1. 把内容指纹编进 chunk_id（版本化 ID）
2. 按页先删后建（用 page_id 前缀定位该页全部 chunk）

**在解决这一条之前做任何增量功能，都是在造脏数据。**

## 六、方案与顺序

| 步 | 做什么 | WAF 成本 | 前置依赖 |
|---|---|---|---|
| 1 | 入库时算 `content_hash` 并落库，同时记 `revision_ts` | 0（纯本地） | 无 |
| 2 | 用 `recentchanges` 拉时间窗内变更标题，与本地 `revision_ts` 比对 | ~6 次元数据请求 | 步 1 |
| 3 | 只对变更页取正文，按页先删后建 | 与变更页数成正比 | 步 1 |
| 4 | 版本共存：chunk 级 `version` 标签 + 查询显式声明要最新还是某版本 | 无 | 步 3 |

顺序不能换：**步 1 不做，步 3 就等于往索引里灌脏数据。**
步 1 完全离线、零 WAF 风险，且做完之后"变没变"立刻变成可判定的事实。

### 步 1 已落地（2026-10-13）

| 项 | 结果 |
|---|---|
| 新增模块 | `app/ingest/fingerprint.py`（归一化 + 页/块两级哈希） |
| 表字段 | `pages.content_hash`（带索引）、`chunks.content_hash` |
| sidecar | `{page_id}.meta.json` 写入 `content_hash` |
| 只读指纹接口 | `pipeline.cached_page_hash()`，不碰正文文件 |
| 迁移 | `scripts/migrate_content_hash.py`（幂等；MySQL 不支持 `ADD COLUMN IF NOT EXISTS`，先查 `information_schema`） |
| 回填 | **1401 页 / 10843 chunk，指纹覆盖 100%**，离线完成，零 WAF 消耗 |

回填前后的页/块/fact 行数完全一致（sr 706/3932/**15017**、ys 435/5413/**5118**、
zzz 260/1498/**4976**），顺带证明了回填是幂等的，没有改动既有数据。

> ⚠️ **别把这组数和 ingest 的 `stats` 混了。** 这里是 **MySQL 最终行数**；
> 而重建索引时 `stats.facts` 报的是**写入量**，两者不等：
> 2026-10-15 实测 `rebuild_index.py` 重跑 ys / zzz，`stats.facts` 是
> **5240 / 6270**，而库里最终是 **5118 / 4976**（差在裁剪与去重）。
> 本行此前写的是 16004 / 5240 / 6270 —— 那是**写入量口径**，
> 被当成了「库里的行数」，所以看起来和 `README:500` 的 25111 对不上。
> 两个数都对，但**引用时必须说清是哪一个**。

#### 归一化不是修饰，是这笔收益的前提

单变量对照实验（`scripts/probe_fingerprint_precision.py`）：
**唯一变量是"哈希前是否归一化"**，语料与扰动方式完全相同
（CRLF 化 + 行尾加空格 + 多一处空行，模拟 wiki 上最常见的无实质改动编辑）。

| 方案 | 1405 页中被误判为"内容变了" |
|---|---|
| 直接对原文取哈希 | **1405 页（100.0%）** |
| 先归一化再取哈希 | **0 页（0.0%）** |

**不归一化的话，"增量"这个方案在数据上直接不成立** ——
每次同步都会把全部页面判成变更，增量等价于全量。
这就是为什么 `normalize_text` 只动不携带语义的差异（换行、行尾空白、连续空行、BOM），
而**刻意保留内部空格**：wikitext 表格的对齐空格有结构含义。

守卫 7 项（`tests/test_content_hash.py`），**双向验证已做**：
把 HEAD 版 `models.py` / `pipeline.py` 注入 `sys.modules` 后实跑，7 项全部变红
（models 换干净 MetaData 加载，否则会撞 "Table 'pages' is already defined"）。

#### 一处刻意的取舍：向量库里还没有块级指纹

`ChunkMeta.content_hash` 已落库，但**没有**往 LanceDB 的 metadata 注入
`content_hash` 字段。原因：现有 7 个 collection 的表 schema 是从首次写入
那批数据推断出来的，往里追加新列对**已存在的表**并不安全，
可能直接抛 SchemaError，而表一坏就是整个索引重建。

所以块级指纹的向量库侧留到**步 3 重建时**一并写入 ——
那时本来就要按页先删后建，schema 问题是顺带解决的。
现在已有的 `chunks.content_hash` 足够支撑"哪些块可以跳过 embedding"的判断，
缺的那一步只是把它搬到离向量更近的地方。

### 步 2 已落地：三级筛变更检测

`app/ingest/delta_sync.py` + `WikiClient.recent_changes()`。

`recentchanges` 一次能列 500 条「被编辑过」的页面，成本极低。
但**被编辑过 ≠ 内容变了** —— 改错别字、调排版都会进这个列表。
所以不能拿着它就开抓，那等于花 WAF 配额去重抓没变的内容。

| 级 | 手段 | 单次成本 | 作用 |
|---|---|---|---|
| 1 | `recentchanges` 时间窗 | 1 请求 / 500 条 | 全站被编辑过的页 |
| 2 | 交集到本地收录 + `fetch_page_meta` 比对 `revision_ts` | 1 请求 / 20 页 | 只留本地有的页，且 revision 未变者直接出局 |
| 3 | 取正文算指纹比对 | 1 请求 / 10 页（带正文） | 只有指纹真变了才算 |

第 2 级的意义：它挡掉「revision 变了但正文没动」的一类编辑
（页面被重新保存、模板被触碰）。只有 revision 也变了的，才值得付取正文的代价。

本地页面清单读的是 MySQL `pages` 表，**不是 checkpoint** ——
checkpoint 只是抓取时的"别重复抓"清单，它不记录指纹，回答不了"变了没有"。

守卫 13 项（`tests/test_delta_sync.py`），全部用假 WikiClient、不碰网络，
重点守**不会多花钱**：revision 未变时禁止取正文、未收录页禁止触发取正文、
本地空语料时禁止发网络请求。

> 本模块是新增的，HEAD 上不存在，因此**没有「修复前快照」可跑双向验证**。
> 这类新增模块靠三件事成立：分流逻辑写成可测的纯函数、断言覆盖每条分流路径、
> 以及必须配一次真实网络实测（否则再绿的测试也只是在测假想）。

#### 守卫当场抓到一个真 bug：翻页游标语义混淆

写完第一版跑守卫，`test_request_counts_are_reported` 直接红了：

```
assert 1 == 8      # 预期翻 1 页，实际翻了 8 次
```

根因：`recent_changes` 返回的 `cursor is None` 有**两种**含义 ——
「还没翻第一页」和「已经翻完、没有下一页」。循环里把它当成前者，
于是每一轮都重新请求第一页。

后果是双重的：WAF 配额白花，`scanned_changes` 虚高成 8 倍，**而且不报错**。
这类 bug 在人工 review 时极难发现 —— 代码看起来完全合理。

修法是显式区分 `first_page` 与 `cursor`，并加了一条独立断言
（`requests.level1 == 1`）把请求量本身锁住，而不只是锁结果。

#### 真实 WAF 实测（2026-10-13 22:14，sr，7 天窗口）

```
本地收录 706 页
全站变更 1157 页（扫到 2922 条，窗口翻完）
交集 162 页
revision 变了但内容没变  0 页
内容实质变化            0 页
请求量 {level1: 6, level2: 9, level3: 0}   合计 15 次
```

三件事值得记：

**1. 15 次请求回答了"哪些页变了"，而全量重抓需要 71 次。**
这正是这套方案的意义——检测成本与语料规模几乎无关，
只与"最近变更量"有关。

**2. 交集是 162 页，不是 148。**
早先探针（`probe_delta_sync_scope.py`）算出 148 并标注为下界，
因为窗口被 WAF 截断在 1003 页 / 2500 条。这次翻完了全部 2922 条，
**162 才是精确值，148 是下界**。凡是被 WAF 截断的读数都不能当结论用——
这条已经吃过一次亏了。

> ⚠️ **但上面那次 162 的运行没有落盘产物。** `data/eval/` 里唯一的
> delta-sync 产物是 `delta_sync_sr_7d.json`，值是 **148 页 / 13 次请求 /
> `lower_bound: true`**。所以引用时必须说清引的是哪一个：引 162 就等于
> 引用一段**只有正文、无法核验**的记录，这与本项目「每个数字都能追溯到
> 产物」的招牌冲突（README 已按两个口径分别标注）。
> 要彻底修掉，重跑一次并落盘即可。

**3. 「内容实质变化 0 页」是正确结果，不是失效。**
当天 21:00 刚补抓过角色页，recentchanges 里的变更大多发生在抓取之前，
所以 `revision_ts` 全部对得上，第 2 级就把 162 页全筛掉了，第 3 级请求为 0。

这恰恰验证了检测器没有把「7 天内被编辑过」误报成「内容变了」——
如果它在这里报出 100 多页"变了"，那才说明归一化没起作用。

> ⚠️ 但也要如实说：**第 3 级（取正文算指纹）在本次实测中未被真实触发**。
> 它目前只有假 WikiClient 的守卫覆盖（`test_delta_sync.py`）。
> 要真正验证，需要隔一段时间语料变旧之后再跑一次。

#### 降级逻辑在真实场景下被验证了

产物 `data/eval/delta_sync_sr_7d.json` 是一次**被 WAF 截断**的运行：

```json
{"local_pages": 706, "scanned_changes": 2500, "unique_changed_site": 1003,
 "intersect": 148, "changed_count": 0, "window_exhausted": false,
 "lower_bound": true, "waf_hits": 2,
 "requests": {"level1_recentchanges": 5, "level2_revision_meta": 8, "level3_content": 0}}
```

| | 修复前 | 修复后 |
|---|---|---|
| WAF 中断时的行为 | 抛 `WAFBlocked`，整轮崩溃 | `waf_hits=2`，保留已读结果 |
| 已读到的 2500 条 / 1003 页 | **全部作废** | 保留，产出交集 148 |
| 是否自报下界 | 来不及 | `lower_bound: true` |
| 进程退出码 | 1 | 0 |

**这正好闭环了文档里那对数字**：这次 148 就是文中说的"早期下界"，
而首次跑通那次翻完了全部 2922 条、交集 162、且 `window_exhausted: true`。
两个数字都真实存在，区别只在窗口是否翻完——被 WAF 截断的读数只能是下界。

顺带修掉一个自己引入的 bug：产物路径用了 `parents[2]`，算成
`backend/data/eval/`——那条路径不匹配 `.gitignore` 里任何规则，
产物会被直接提交进仓库，且永远不出现在文档引用的位置上。
现由 `test_artifact_dir_is_project_data_eval` 守住。



### 这笔账（按实测参数）

| | 全量 | 增量 |
|---|---|---|
| 检测请求 | — | **15 次**（实测 6+9） |
| 抓取请求 | 71 批 × 6s ≈ 7.1 分钟 | 17 批 × 6s ≈ 1.7 分钟 |
| 重新 embedding | 3932 chunk | ≈ 908 chunk（**省 77%**） |
| 限流风险 | 低（已验证 886 页 0 拦截） | 元数据阶段偏高（实测 6s 必撞，需 15s） |

结论：**增量值得做，但收益主要在 embedding 成本而非抓取时间**。
时间省约 75%，embedding 省约 77%——两者接近，
说成"增量省了 79% 时间"是不准确的。
而且要接受"变更检测本身就要占 WAF 配额"这个事实。

## 七、面试怎么讲

不要讲"我做了个知识库"，讲这三句：

1. **我知道知识库真正的难点不是检索，是失效传播。**
   我的语料 30% 是两年多以前的内容，实测时间过滤能把陈旧页从 77.2% 清到 0 ——
   但那是事后过滤，版本更新要解决的是事前检测。

2. **我算错过一次口径，而且是自己发现的。**
   一开始只看全站变更页，算出"一周变更 1157 页 vs 全库 706 页"，
   差点得出"增量没意义"。换成交集口径后是 162 页、23.0%，结论直接反转。
   **增量成本的分母必须是你会同步的那个集合，不是站上总页数。**

3. **我知道真做增量会踩什么坑。**
   chunk_id 由 page_id 派生，页面改了 ID 不变，旧 embedding 会被静默当成有效 ——
   比不同步更危险。所以顺序是先落内容指纹，再做增量检测；
   而指纹必须做归一化，否则实测 1405 页会被 100% 误判成"全变了"。
