# 失败案例分析

> 这份文档回答一个比"跑分多少"更能证明能力的问题：**这套系统在哪儿会出错，为什么。**
>
> 数据来源：`data/eval/exp_A.json`、`data/eval/exp_C.json`（每份都带 `_meta` 出处块，
> 记录了产生它的脚本、UTC 时间与 git commit）。原始逐条得分与 Judge 理由都在文件里，
> 这里的每一条结论都能回溯到具体 `case_id`。
>
> 分类维度取自 `plan.md` 的 Definition of Done：检索失败 / 生成幻觉 / 工具选错 / 循环不终止。

---

## 一、结论先行：四类失败，性质完全不同

| 类型 | 数量 | 危险程度 | 能不能靠"再调参"解决 |
|---|---|---|---|
| A. 检索没找到 | 1 / 29 | 低 | 能（加 k、改分块） |
| B. 纯向量在专有名词上翻车 | 2 / 29 | 中 | 不能，必须靠混合检索 |
| C. **答案对但引用了不存在的页面** | 3 / 15 | **高** | 不能，是生成层的忠实度问题 |
| D. **无工具时模型输出内部标记** | 5 / 15 | **高** | 能（改调用方式，已改） |

**最值得讲的是 C 和 D。** 它们都出现在「正确答案」这个表象之下，只看均值发现不了：

- C 类：`correctness = 5.0`（答案完全正确），`faithfulness = 2.0`（引用是编的）。
  均值被 correctness 拉得很高，但忠实度指标就是为了揭穿这一层。
- D 类：模型的回答里混进了 `<tool_call>` / `<｜｜DSML｜｜>` 这类**内部协议标记**，
  用户看到的是一段乱码而不是答案。

## 二、A 类：检索没找到（1 条）

`sr-015`（semantic）
> 火属性的首领打不动，wiki 上说应该用什么属性配队比较好？

- gold 页面：`凝滞虚影 • 炎华之形`
- **A0 BM25 命中 / A1 向量未命中 / A2 融合未命中 / A3 完整链路未命中** —— 四档全灭
- 29 题里唯一一条 A3 也召不回来的

**为什么** 这题问的是**配队策略**，而答案页面是「炎华之形」的数值表。
问题里的词（"火属性""首领""配队"）在目标页面上根本不出现，
BM25 没有词面可锚；向量检索则因为问题与页面的表述不同构而漂走。

**归因**：这类题（"该带哪个""怎么配"）在当前语料结构下是**结构性难题** ——
wiki 记的是"这个 boss 的属性"，没记"所以你应该带什么属性"。
补 `chunk_size` 或加大 `top_k` 都不会解决，因为候选集里压根没有能回答它的句子。

**如果要做**：这是 query 改写（多查询扩展）的典型靶子 ——
把"火属性首领打不动该配什么属性"改写成"炎华之形的属性克制/配队推荐"就能命中。
当前项目没有 query 改写，所以这题是已知的、未修复的能力边界。

## 三、B 类：纯向量在专有名词上翻车（2 条）

`sr-007`、`sr-012`（均为 semantic）

| case | 题干 | gold | A0 BM25 | A1 向量 |
|---|---|---|---|---|
| sr-007 | 我攻击力不够还想更快，用哪个位面饰品比较合适？ | 太空封印站 | mrr **0.333** | mrr **0.0** |
| sr-012 | 队伍里效果抵抗不够高，想让全队的暴击伤害更高，有什么套装？ | 折断的龙骨 | mrr **0.333** | mrr **0.0** |

**这两条是整个项目最有说服力的实验证据。**

两条题干**都不含任何道具名**，只有目标状态描述。BM25 靠"攻击力""暴击伤害"
这类通用词偶然蹭进相关页面（排第 3，mrr=0.333）；纯向量检索反而**全军覆没**
（mrr=0，即 top-3 里一次都没出现 gold 页）。

**这正是 README 开头立论的实测版本**：
> 大量低频专有名词（位面饰品、行迹、命途…）——纯向量检索一定翻车。

它不是"向量检索不好"，而是**向量检索在没有词面锚点、且专有名词占比极高时无处落脚**。
A2 融合把这两题救回到 0.897，A3 重排再推到 0.966 —— 混合检索 + 重排的收益
有三分之二来自这种"向量单独会翻车"的题，而不是来自"向量更强"。

## 四、C 类：答案正确，但引用了不存在的页面（3 条）

这是**最危险**的一类，因为它在均值里完全看不出来。

| case | correctness | faithfulness | Judge 理由 |
|---|---|---|---|
| sr-007 | **5.0** | **2.0** | 正确推荐太空封印站，但提及不存在的不老者的仙舟 |
| sr-011 | **5.0** | **2.0** | 推荐正确但提及不存在的饰品 |
| sr-013 | **5.0** | **2.0** | 正确提及生命翁瓦克效果，但劫火莲灯等套装无证据支持 |

**形态**：C1/C2 已经挂了 `search_kb`，检索结果是有的，但模型在**组织答案时
自己加戏** —— 把记忆里的、检索结果里没有的套装名（不老者的仙舟、沉陆海域露莎卡）
当作引用写了出来。

**为什么危险**：如果只看 `correctness` 或只看总分，这三条是满分题；
用户点开引用却发现链接打不开 —— **可核查性直接崩塌**。
这正是 `faithfulness`（忠实度）指标存在的理由，也是为什么实验 C 要把
correctness 和 faithfulness **分开报**而不是合成一个分。

**当前处置**：项目只做到"标注"，没做到"拦截"。回答里的每个 `[页面名]` 引用
目前由模型自己生成，没有与检索结果做交叉校验。
**能立刻做的改进**：生成后校验每个引用是否出现在本轮检索结果里，
不在就剥掉或标红。这是个小改动，但把"可核查"从承诺变成机制。

## 五、D 类：无工具时模型输出内部协议标记（5 条）

C0（不挂任何工具）的回答里出现了这种东西：

```
sr-001 → <｜｜DSML｜｜ calls>  <｜｜DSML｜｜ invoke name="search_kb">
sr-002 → <｜｜DSML｜｜ calls>  ...
sr-004 → <ds_safety>[用户未成年]否 ... </ds_safety>Safe
sr-006 → 我先查一下知识库…  <tool_call>{"name":"search_kb",…}</tool_call>
sr-008 → <｜｜DSML｜｜ calls>  ...
```

**成因**：模型是在带工具协议上训练的。即使不给你工具声明，它仍会按训练时的格式
"硬凑"一次工具调用，把内部标记当正文吐出来。sr-004 还吐出了它的安全分类中间态。

**为什么这条要专门记**：它在 `EVALUATION.md` 里叫"附带发现：无工具时模型仍会硬凑工具调用"。
现在有了它对**质量分数的量化影响** —— C0 的 `single_hop` 题型只有 2.00 分，
而 C1/C2 是 5.00 分。这里面有一部分不是"模型不知道"，而是"模型答非所问"。

**已处置**：`exp_c.py` 里 C0 走单轮问答而非 ReAct 循环，避免模型收不到
`tool_calls` 声明后反复尝试调用。生产链路里 `search_kb` 始终开着，这个坑不会外泄。
但记录它有意义：**它解释了为什么"不挂工具"不是"关掉工具"的等价物。**

## 六、还没有被记录的失败类型

plan.md 要求的四类里，**「工具选错」与「循环不终止」在本次实验数据里没有出现**：

- 工具选错：C1 的 `tool_failures` 率为 0.087（约 1.3 次/15 条），C2 为 0.000。
  说明两个档位都没有明显选错工具的情况。
- 循环不终止：`agent_max_steps` 兜底生效，本轮 15 条没有触发步数上限。
  （历史上修过一次"连续 7 步空转 / 30317 tokens"的问题，见 README 的熔断说明。）

**这里要如实说明的是**：这两类"没有出现"，样本量 n=15 下**不足以证明不存在**，
只能说"本轮没观测到"。熔断路径仍然只有探针级的验证，没有在评测集里覆盖到 ——
这是当前评测的一个真实盲区。

## 七、从失败里能得出的三条工程结论

1. **忠实度必须独立成指标。** C 类失败说明 `correctness=5` 与"用户点开引用能找到"是两件事。
   把它们合成一个分数，就等于把最危险的问题藏起来了。

2. **失败模式决定优化方向。**
   - A 类（检索找不到）→ 加 query 改写、加 top_k
   - B 类（向量翻车）→ 混合检索 + 重排（已做，收益最大）
   - C 类（编造引用）→ 生成后校验，这是**下一步最该做的一个改动**
   - D 类（格式外泄）→ 调用方式设计（已做）

   三类的解法完全不同，所以"哪个指标低就调哪个参数"是错的。

3. **n=15 看不见的东西不等于不存在。** 工具选错与循环不终止属于低频故障，
   15 条题碰不到。要覆盖它们，需要的是**故障注入测试**（plan.md 的 DoD 之一，
   尚未实现），而不是把评测集从 15 条扩到 30 条。
