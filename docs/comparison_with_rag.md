# 这个项目与常见 RAG 知识库的区别、差距与亮点

> 这份文档回答一个具体问题：**当我说「我做了一个 RAG 知识库问答 Agent」时，
> 面试官接下来会问什么，而我手上的证据能不能接住。**
>
> 写作纪律与本项目其他地方一致：
> - 每个数字都能追溯到 `data/eval/` 下的产物或某个 doc；
> - **不写未经测量的对比**。市面产品的内部实现我拿不到，所以下面凡涉及
>   「别人怎么做」的陈述，一律按公开文档的通行做法描述，并标注这是外部认知而非实测；
> - 差距一节写得比亮点长，因为**知道自己缺什么比会说自己强更能证明工程能力**。

---

## 一、一句话定位

> 常见 RAG demo 交付的是「答案像样」；这个项目交付的是
> **「你能查到它凭什么这么答，以及它什么时候不该被相信」**。

差别不在模型，在**可核对性**：每条回答都挂着工具过程、出处页面修订日期、
检索步数、token 消耗与终止原因，并且这套元信息能被一键导出成 Markdown 供人复核。

---

## 二、五条实打实的差异

### 1. 结论带统计显著性和样本量，不带就明确说没测

多数 demo 会写「我们用了混合检索 + 重排，MRR 提升明显」。本项目的写法是：

| 维度 | 结论 | 限定条件（与结论同等重要） |
|---|---|---|
| 重排（A3） | sr recall@3 0.793 → **0.897** | ⚠️ **ys/zzz 在纯向量档就已打满（1.000），重排无提升空间 —— 这条只有 sr 有样本支撑** |
| `embed_mode` | sr MRR 0.736 → 0.506（**−23.0pt, p=0.0001**） | ys −13.3%、zzz **0.0%**；只有 sr 达显著 |
| Chat 基座 | 三库 Δ 均未达显著（p=0.070/0.674/0.283） | **明确写「不敢说谁更强」**；成本差异反而三库一致 |
| 披露层（F） | 撤掉后 15 个目标页日期命中 15 → **0** | F1 的 0 是**机械必然**（工具输出本就没日期），不能读作「加披露层让模型变强」 |

出处：`data/eval/exp_A_all_k3.json`、`exp_B{0..3}_{sr,ys,zzz}_k3.json`、
`exp_E_{sr,ys,zzz}.json`、`exp_F.json`，详见 `EVALUATION.md`。

**这是最难被模仿的一条。** 大多数候选人不会去查 p 值，而查了之后还愿意
把「不显著」写进简历的更少。

### 2. 主动暴露被自己数据推翻的结论

同一个项目里，有两条结论是被自己的实测**推翻**的，而且推翻过程完整保留在文档里：

- **「页面修订时间久 = 内容过时」**：聚类实测发现三库修订日期按版本节点聚集
  （Top12 日期占 40%~60%），说明 wiki 是批量维护 —— 「页面久未编辑」
  推不出「内容已过时」。所以**陈旧告警这个功能被主动放弃**，时间戳只当溯源用。
  产物 `probe_revision_clustering.json`。
- **「一条判据能证明模型更诚实」**：原设计的「修订措辞率」指标，
  离线重算后发现消融档反而更爱说「修订」（F1=0.25 / F2=0.00，
`data/eval/exp_F.json` 的 `has_revision_wording_rate`）——
  它量的是用词习惯，与披露负相关。该指标被**撤回**，
  代码里留了常量 `_REVISION_WORD_METRIC_RETRACTED` 记录这件事。

**能力边界被当成一等公民写进设计**：文档明确写着「披露层有没有让回答更准，
本语料无法验证 —— 每页只有最新版快照，没有历史版本可比对」。

### 3. 手写 ReAct，且把「不该回答」当成一类结果

- 工具调用过程**全程在界面上可见**（检索了什么、多久、返回多少字符），
  不是黑框转圈。
- 知识库里没有的内容，不会编：越界游戏走**无工具单轮**，实测 0 步 / 1.1s。
- 成本控制是真做了：不可答问题从 7 步 / 30317 token 降到 **4 步 / 6514 token**
  （SearchGuard 熔断）。
- 提示注入：11 条规则分两级，10843 chunk 真实语料误报 **0**，
  攻击样本召回 **13/13**，工具结果一律包进不受信任数据区
  （`docs/injection_guard.md`、`data/eval/injection_scan.json`）。

### 4. 交付物模式：不只是回答，而是可交付的文档

除了问答，还有一条 `/api/deliverable`：把「整理三月七的养成指南」
拆成多个子任务，各自检索、抽取结构化事实、去重、标冲突，产出
Markdown + JSON 两份文件。

里面有两处**踩坑后修掉**的痕迹，都写进了代码注释：

- **主题闸门**：模型会把别的角色页抽进来（实测三次分别拦下 6 / 4 / 5 条）。
- **去重不能过头**：`relic_set` 同 key 同值但 label 不同（「隧洞遗器1/2/3」）
  是**三个不同槽位**，误当重复会吃掉两条。比较维度必须包含 label。

### 5. 整个仓库可复现

`data/eval/` 下每个产物都带 `_meta`：产生它的脚本名、UTC 时间、git commit、
Python 版本、平台、并发度、缓存冷热、top_k、rerank_candidates……
CI 跑 pytest + ruff + 前端测试 + 前端构建 + 密钥卫生（且 `fetch-depth: 0`
是**功能性要求**，否则三条双向验证守卫会全部 skip —— 这件事写进了 CI 注释）。

## 三、差距：诚实地列出来

这一节比上一节长。列在这里是因为**面试时主动说出差距，比被问出来强得多**。

| 维度 | 现状 | 缺什么 | 影响 |
|---|---|---|---|
| **语料规模** | 1401 页 / 10843 chunk，三个游戏 | 真实企业 RAG 面对的是百万级文档 | 没有验证索引方案在规模上的表现 |
| **向量检索** | LanceDB 暴力精确扫描，实测毫秒级 | 没有 ANN（无 IVF/HNSW），也没做索引选型对比 | 规模上去必然退化，当前「毫秒级」结论**不可外推** |
| **评测集规模** | 生成侧 ys/zzz 各 12 条 | 经验上单库要 30+ 才谈显著性 | C1→C2 的差异三库方向不一致，**目前无法断言是真实结论还是题型构成造成的假象** |
| **增量同步** | 测了「变更页 ∩ 已收录 = 23%」 | **没有真正实现并跑通增量入库**，只做了收益测算 | 文档里写的是「机制验证」，不是「已上线」 |
| **多轮对话** | 有历史裁剪（字符预算） | 没有多轮指代消解的评测 | 「它」「这个角色」类问题没有测过 |
| **权限与多租户** | 无 | 完全没有 | 企业场景的第一道门槛 |
| **评测维度** | correctness / faithfulness / completeness | 没有时效敏感度、没有忠实度独立分 | judge 三维**没有一维评时效**，所以 F 实验只能用正则判据 |
| **部署** | 本机 uvicorn + vite | 无 Docker、无 K8s、无监控告警 | 工程化完整度不足 |

另外**已知且未修**的坑，都在文档里显式声明了。
其中两条已在 2026-10 补上，但**补得不完整**，这里按现状重列：

1. ~~**故障注入测试从未实现**~~ → **已实现**（`backend/tests/test_fault_injection.py`，23 条）。
   但要分清两件事：熔断路径从此前的「只有探针级验证」升级为「有端到端断言且经过
   双向验证」；而**评测集里仍然没有覆盖到熔断** ——
   「机制被验证过」与「在真实问题分布上被观测过」不是一回事，目前只有前者。

2. ~~**C 类（编造引用）的生成后校验未实现**~~ → **已实现 L1/L2，未实现 L3**。
   L1 形状闸门（方括号内容像不像页面名：含中文、非纯数字/版本号、不在代码跨度里）
   → 不像的**不参与剥除**，记进 `skipped`；
   L1 页面级（过了形状闸门、但页面不在本轮取到正文的页面里）→ 剥除 + 计数；
   L2 数值级（句子里的数字在该页正文里查不到）→ **只记录、不改文本**
   （推导值会被误判，削掉正确的计算过程比留着更糟）；
   **L3 语义级（句子是否真的被该页正文支持）仍未做** —— 需要逐条比对答案与
   chunk 正文的语义，得额外调模型。
   所以「C 类失败已被拦截」这句话**只对 L1 成立**：
   一句不含数字、也不引用不存在页面的编造，L1/L2 都抓不到。
   另外 L1 **不再宣称「零误报」**（曾经宣称过，是错的）：形状像页面名、
   但其实是正文里别的方括号用法（`[详见上文]`）仍会被剥，属于已知代价，
   见 `failure_analysis.md` 第四节。

3. **judge 有间歇性 120s 超时**，sr 档有 3 条被判剔除（n_ok 29/32），
   而被剔除的恰是难题 —— 所以 judge 均值必须连着 `n_ok/n` 一起读。

## 四、面试时该怎么讲

### 不要这样讲

> "设计了版本感知检索，解决了过期知识问题。"
> —— 没有证据支持「解决了」，而且聚类实测证明这个前提本身站不住。

> "接入了时间戳，所以回答更准确。"
> —— 披露层对准确率的影响**从来没测过**，而且原理上就不该被当成新鲜度信号。

> "我们的 RAG 效果很好，MRR 提升了。"
> —— 三库里两库在纯向量档就打到 1.000，这个「提升」在 sr 之外不存在。

### 应该这样讲

> "我做的是一个垂直领域知识库问答系统，三库 1401 页。
> 和一般 demo 最大的不同是我把**可核对性**做进了产品：
> 每条回答都挂着工具过程、出处页面的修订日期、检索步数和 token 消耗，
> 一键能导出成 Markdown。
>
> 更重要的是我敢用统计显著性说话：A0–A3 四档检索、
> C0–C2 三档 Agent 能力、E1/E2 两个基座，全部逐库配对检验，
> 三库**都**给了 p 值和效应量。但**必须说清是哪一步**：
> BM25 → 完整链路这一步在 sr 上有效（recall@3 0.793→0.897，A0→A1 p=0.0362 显著）；
> 而 A1→A2（融合）**Δ=0.0000、p=1.0000，没有测出增益**，
> A2→A3（重排）**p=0.0850，在 sr 上也没过 0.05**
> （只有 48 条合计口径 p=0.0261）。在 ys/zzz 上纯向量就打满了 1.000，
> 所以**这条结论只有 sr 有样本支撑** —— 我不会拿它去跨库宣称。
> 更不会说「重排 p<1e-10」：那个数量级在本项目的检索消融里**一格都没有**。
>
> Chat 基座对比我做出来的结果是三库全部未达显著，所以我**没敢下结论**，
> 只记下了成本差异（MiniMax token ×1.55~2.85、延迟 ×2.56~3.65）。
>
> 还有一件事我做了但很多项目不会做：我推翻了自己的第一版设计。
> 我本来想按页面修订时间做「陈旧告警」，实测发现三个 wiki 的修订日期
> 按版本节点聚集（Top12 日期占 40~60%），是批量维护不是逐页维护 ——
> 「页面久没动」推不出「内容已过时」。所以我把这个功能**删了**，
> 时间戳只当溯源信息展示，不当新鲜度评分。
>
> 我也很清楚剩下什么没做：没有 ANN 索引（所以现在的毫秒级结论不可外推）、
> 生成侧 ys/zzz 只有 12 条题、C 类的『引用是否真的支持这句话』还没校验。
> 这些我写在 README 的『下一步』里了。"

### 为什么第二种讲法分量更高

它同时展示了：**机制设计能力**、**知道自己结论的适用范围**、
**主动推翻自己**、**敢报告阴性结果**、以及**主动暴露项目缺口**。

最后一点尤其稀缺——绝大多数候选人不会主动说自己缺什么，
因为面试官问的是「你有什么优势」，主动交代缺口的心理成本很高。
而它恰恰是**唯一能让面试官相信你前面所有优势都是真的**的方式：
一个敢说自己缺什么的人，说「我的检索效果很好」时才值得信。
