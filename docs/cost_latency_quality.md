# 成本 / 延迟 / 质量：为什么生产只开 `search_kb`

> 数据来源：`data/eval/exp_C.json`（带 `_meta` 出处块）。
> token 数逐条存在文件的 `rows[].prompt_tokens` / `completion_tokens`，可回溯。
>
> **口径提醒**：本表延迟跑在 `--concurrency 2` 下，含排队时间，
> **不可与串行跑的延迟数字直接比**（见 `docs/experiments.md` 的「四个坑」第 3 条）。
>
> ⚠️ **这份产物是 legacy 单库 15 条口径**（`exp_C.json`，C0 提示词缺陷修复前的运行）。
> 当前三库逐库的产物是 `exp_C_{sr,ys,zzz}.json`，**口径不同、数字不可直接比**：
> 本表 C1/C0 = **×19.9**、C1→C2 = **+8.1%**、judge +0.13；
> 当前 sr 是 **×9.8**、**+17.2%**，且 C1→C2 的 judge **方向相反**（−0.13）。
> README 那行此前写的 ×20.2 / +23% 三个口径都不是 —— 已按两边分别标注。

## 一、三档对照（n=15，每档同一批题）

| 档 | 工具 | judge | correctness | faithfulness | prompt tok | 完成 tok | 平均步数 | 引用率 | 工具失败 | 延迟 |
|---|---|---|---|---|---|---|---|---|---|---|
| **C0** | 无 | **2.43** | 1.60 | 3.27 | **2,849** | 1,200 | 0.0 | 0% | 0 | 986ms |
| **C1** | `search_kb` | **4.67** | **5.00** | 4.33 | **56,681** | 4,663 | 1.5 | **100%** | 2 | 3627ms |
| **C2** | 全套 4 个 | **4.80** | 5.00 | 4.60 | 61,272 | 4,986 | 1.7 | 93% | 0 | 3185ms |

**挂上知识库的代价**：prompt token 从 2,849 涨到 56,681，**×19.9**。
原因很直白：C0 一个工具都没调，没有检索上下文；C1/C2 每条都要把召回的页面片段塞进 prompt。
延迟也从 986ms 到 3.2–3.6s，**约 3.5 倍**。

这笔钱花得值不值，看质量侧：judge 从 2.43 → 4.67，**+92%**。
correctness 从 1.60 直接拉满到 5.00。所以答案是值 —— 但要清楚代价是多少。

## 二、C1 → C2 是本表最该讲的一段

| 变化 | C1 → C2 |
|---|---|
| judge | 4.67 → 4.80（**+0.13**） |
| correctness | 5.00 → 5.00（**+0.00**） |
| prompt token | 56,681 → 61,272（**+4,591，+8.1%**） |
| 平均步数 | 1.5 → 1.7（+0.2 步） |
| 工具失败次数 | 2 → **0** |

**多花 8% 的 token、多半步工具调用，换来 2.8% 的分数提升，而 correctness 一点没动。**

这就是"生产环境只开放 `search_kb`"的完整依据 —— 不是拍脑袋，是算出来的：
另外三个工具（`get_page` / `calculator` / `list_games`）在当前评测集上**没有带来
可测量的正确性收益**，只增加了成本、步数和失败面。

⚠️ 这个结论的边界要说清楚：n=15，且当前题库里**没有真正需要 `calculator` 的数值题**
（sr-008 是唯一一道，模型用 C1 也能答对）。如果题库里多几道"攻击力 1000 换算成伤害"这类题，
`calculator` 的价值应该会显现 —— 现在测不出 ≠ 这工具没用。

## 三、按 token 折算的量级（供估算，非账单）

> 以下金额按 DeepSeek 公开价格档（输入 ¥1 / 百万 token、输出 ¥2 / 百万 token）估算，
> **下单前请自行核对当时的官方价目**。不含 Judge 调用、embedding 与 rerank 的费用 ——
> 那部分 bge-m3 与 reranker 在硅基流动上是免费档。

| 档 | 15 条 Chat token（输入+输出） | 估算金额 |
|---|---|---|
| C0 | 2,849 + 1,200 | ≈ ¥0.005 |
| C1 | 56,681 + 4,663 | ≈ ¥0.066 |
| C2 | 61,272 + 4,986 | ≈ ¥0.071 |

**量级判断**：这个规模的用户量下，Chat 成本**几乎可以忽略**（几分钱一轮评测）。
真正贵的是 embedding 重建索引 —— 一次全量重建三库合计 10843 个 chunk
比整个 C 实验的 Chat 花费高几个数量级。

这个结论有个实际推论：**不要为了省 token 去优化回答质量。**
省下的钱（¥0.06）在真实业务里根本不是决策依据，该按质量选型。
token 成本应该用"每条问答"的绝对值判断，而不是"相对 C0 涨了多少倍"——
C0 那个基数低得没有可比性。

## 四、延迟怎么看

| 观察 | 说明 |
|---|---|
| C0 986ms | 纯生成，几乎不花钱也不花时间，但答案是错的 |
| C1/C2 3.2–3.6s | 检索（本地 BM25+向量 8ms）+ rerank（远程 300–450ms）+ 生成的**串行叠加** |
| C2 比 C1 快 | **不是**因为工具更高效，而是并发下的排队波动，样本内不可复现 |

真正压延迟的手段不是砍功能，是**让等待不阻塞用户** ——
流式（SSE）把 TTFT 从 3410ms 压到 860ms，实测数据见 `data/eval/probe_stream_latency.json`。
「总耗时差不多但用户感知快 4 倍」是本项目延迟优化里唯一可复现的结论。
