# 重排（Rerank）是什么

一篇文档，专门把「重排」这件事讲透。前面几份文档都假设你已知这个词，
这份不假设 —— 读完你应该能回答面试官的任何追问。

---

## 一句话

> **召回**负责「把可能对的都捞进来」，**重排**负责「把最对的排到最前面」。

检索其实是两件事，问题出在大多数系统只做了第一件。

---

## 先看它要解决什么问题

假设有人问你：

> 「我攻击力不够还想更快，用哪个位面饰品比较合适？」

注意：这句话里**没有任何一个道具名**。这叫纯语义查询。

### 只有召回时会发生什么

我们的检索链前三步（BM25 稀疏召回 → 向量稠密召回 → RRF 融合）跑完，
拿到的候选大致长这样：

| 名次 | 页面 | 命中原因 | 对不对 |
|---|---|---|---|
| 1 | 繁星竞技场 | 含「攻击力」「速度」等词 | ⚠️ 相关但不是最优 |
| 2 | 太空封印站 | 语义相近 | ✅ **真正对的** |
| 3 | 折断的龙骨 | 含「攻击力」 | ❌ 不相关 |
| 4 | 生命的翁瓦克 | 语义相近 | ⚠️ 次优 |
| 5 | 奇想蕉乐园 | 语义相近 | ⚠️ 一般 |

**真正正确的答案在第 2 位。**

如果你只取 top-1，模型看到的是「繁星竞技场」——
它会照着错的页面回答，而且答得很自信，因为模型不知道自己拿错了。

### 重排之后

把上面这 31 条候选（融合后）送进 Cross-Encoder 重新打一次分，
排序变成：

| 名次 | 页面 | 重排分数 |
|---|---|---|
| 1 | **太空封印站** | 0.931 |
| 2 | 繁星竞技场 | 0.827 |
| 3 | 生命的翁瓦克 | 0.790 |
| … | | |

**第 2 名变成第 1 名。** 这就是重排的全部作用。

---

## 为什么召回和重排不能用同一套逻辑

这是理解重排的关键，也是面试最常被追问的点。

| | 召回阶段（第一阶段） | 重排阶段（第二阶段） |
|---|---|---|
| 要处理多少条 | 全部 2306 个 chunk | 只处理 top 20–31 |
| 每条要算几次 | 1 次 | 1 次 |
| 用什么模型 | 向量模型（双编码，一次编码全文） | Cross-Encoder（交叉编码） |
| 怎么算相似度 | 问题编码一次，文档编码一次，**互相看不见对方** | 问题和文档**拼在一起**送进模型 |
| 能理解「这段话和这个问题矛盾吗」 | ❌ 不能 | ✅ 能 |
| 耗时 | 本地 8ms + 远程 147ms | 远程 449ms |

**双编码（bi-encoder）为什么不够用**：

它把问题和文档分别压缩成一个向量，**就像把两个人各自关在房间里写自我介绍，
然后让第三方比对他们写的介绍**。介绍里可以写「我是速度流的遗器」，
但没法体现「这句话恰好回应了那个具体问题」。

**交叉编码（cross-encoder）怎么做**：

把「问题 + 文档」拼成一句话送进模型：
`"我攻击力不够还想更快，用哪个位面饰品比较合适？[SEP] 太空封印站：使装备者攻击力提高12%……"`

模型能读懂两者之间的对应关系 —— 甚至能发现矛盾
（「你问的是速度，但这篇讲的是暴击率」）。

**代价**：交叉编码必须把每条候选都单独送一遍模型，无法预计算，
所以只能用在少量候选上（我们送 20 条），不能用在全量 2306 条上。

## 在我们的代码里，它在哪一行

```
HybridRetriever._rerank()                    backend/app/retrieval/hybrid.py:280
  ├─ 取出融合结果的前 rerank_candidates 条（默认 20）
  ├─ llm.rerank(query, 候选文本列表)          backend/app/llm/client.py:174
  │     └─ POST https://api.siliconflow.cn/v1/rerank
  │           model = BAAI/bge-reranker-v2-m3
  └─ 按重排分数重新排序，取 top_k
```

外部调用就一行 HTTP：

```json
POST https://api.siliconflow.cn/v1/rerank
{
  "model": "BAAI/bge-reranker-v2-m3",
  "query": "我攻击力不够还想更快，用哪个位面饰品比较合适？",
  "documents": ["太空封印站：使装备者攻击力提高12%...", "繁星竞技场：...", "..."],
  "top_n": 20
}
```

响应直接给每个文档的相关度分数，按分降序。

## 它的实测效果与代价

数据来自 `EVALUATION.md` 实验 A（n=29 条评测题，top_k=3）：

| 配置 | recall@3 | MRR | NDCG | 延迟 |
|---|---|---|---|---|
| A2 融合（**不开**重排） | 0.897 | 0.874 | 0.879 | 221ms |
| A3 融合 + 重排 | **0.966** | **0.966** | **0.966** | **567ms** |
| 差值 | **+6.9pt** | **+9.2pt** | **+8.7pt** | **+346ms（2.6 倍）** |

**收益**：是整个检索链里提升最大的一步，把 top-3 命中率从 0.897 拉到 0.966。

**代价**：检索延迟从 221ms 涨到 567ms。实测它占了检索耗时的 **94%**
（关掉重排后检索只要 41ms，开着要 764ms）。

### 所以它该开还是该关？

看你要什么：

| 场景 | 建议 | 理由 |
|---|---|---|
| 面试演示、效果优先 | **开** | 0.966 vs 0.897，差距一眼能看出来 |
| 高并发线上服务 | 关 | 41ms vs 764ms，差 18 倍 |
| 只取 top-1 给模型 | **开** | 错的 top-1 会导致整段回答都错 |
| 只取 top-10 给人看列表 | 关 | 反正 10 条都在，重排影响不大 |
| 兜底降级（API 挂掉） | 关 | 实测过降级路径，0.897 仍可用 |

**这也是前端检索面板存在的意义** —— 三个开关（BM25 / 向量 / 重排）能当场
把这个权衡演出来，而不是让你背一张表格。

## 三个常见的误解

**误解 1：「重排是可选的优化，不开也能用」**

数字上确实能用（0.897）。但注意 A2 的失败模式是**把对的答案排在第 2 位**，
而模型只拿 top-1 时会答错。**排名靠后比召不回更容易造成「自信的错误答案」。**

**误解 2：「重排就是把分数重新算一遍」**

不是。召回阶段也有分数，但两者的分数**不能直接比较** ——
BM25 分数是无界正数，余弦相似度在 [-1,1]，Cross-Encoder 的相关度又是另一套刻度。
所以 RRF 阶段用排名不用分数（`Σ 1/(60+rank)`），重排阶段才重新引入分数。

**误解 3：「换个 embedding 模型也能替代重排」**

实验 D 实测：换成 `Qwen/Qwen3-Embedding-0.6B` 后，
纯向量 MRR 从 0.828 变成 0.776。
但**同一批 29 条上的跨模型配对检验显示这个差异未达显著**
（A1 Δ=+0.0517、p=0.3673、Cohen's d=0.133），
**不能据此说「更差了」** —— 能说的只是「两者在本语料上区分不出来」。

不过这不影响本条误解的结论：**换 embedding 并没有省掉重排要解决的问题。**
重排解决的是排序，而 Qwen 与 bge 在 A1/A2 的排序能力无法区分，
所以没有任何证据表明换 embedding 能替代 rerank。
另外 `bge-reranker-v2-m3` 只认 bge 系，换 embedding 模型反而可能不适配。

## 如果面试官问「你会怎么优化重排」

按收益排序（前三条已实测，后两条是查证过公开基准的判断）：

1. **裁剪候选数**（已做）：31 → 20 条，省 14.8%，指标逐位不变
2. **结果缓存**（已做）：同一 query + 同一候选集直接复用，省 449ms
3. **按 top_k 自适应**：要 top-1 就重排 10 条，要 top-10 就重排 30 条

> ⚠️ **第 1 条的 14.8% 是冷缓存口径，必须说清楚，否则会被追问穿。**
> 它来自 `run_eval.py` —— 每个 label 前都 `llm.clear_caches()`，测的是**首次问**那条路。
> 我另外用 `bench_latency.py` 在**两组都预热过**的热缓存下重测，
> 中位数只从 31.7ms 降到 31.1ms（**-2.0%**），均值 -6.0%
> （`data/eval/bench_latency_rerank_cut.json`，`_meta.context.warm_cache = true`）。
>
> 两个数字都对，差的是缓存状态：**裁剪省的是"那次真的调用远程 rerank"的成本**；
> 一旦缓存命中，裁不裁几乎没差别。
> 讲的时候按"重复提问多不多"选口径，别混着说。
>
> 顺带一个真实翻车：修之前这个探针只预热了第一条 query，
> 剩下 14 条的冷启动全落在**先跑的对照组**上，于是打出"对照组均值 228ms、
> 实验组 121ms，省了一半" —— 同一份代码隔一分钟重跑，中位数就从 +18.4% 变成 -31.2%。
> 那不是抖动，是"谁先跑"混进了变量。

4. ⚠️ **本地跑 Cross-Encoder —— 能省钱，但别指望它更快**

   我原本以为把 reranker 搬到本地就能降延迟。查了公开基准后发现**恰恰相反**：

   | 方案 | 20 条候选耗时 | 备注 |
   |---|---|---|
   | **SiliconFlow API（本项目当前）** | **449ms** | 跑在数据中心 GPU 上 |
   | bge-reranker-base 本地 CPU（PyTorch） | ~2740ms | 实测 P50 |
   | bge-reranker-base 本地 CPU（ONNX） | 约 2× 于 PyTorch，但仍是秒级 | ONNX 优化的是相对 PyTorch，不是相对 GPU |
   | bge-reranker-v2-m3（更大的模型） | 更慢 | 参数量 568M |

   **原因是本项目跑在 SiliconFlow 的 GPU 上，而本地是纯 CPU 且无 GPU。**
   ONNX 转换能带来 2 倍加速，但那是在 PyTorch-CPU 基准内部比较，
   追不上一个有 GPU 的远程服务。

   本地化真正的价值是另外两件事：
   - **省钱**：无 API 调用费
   - **消除外部依赖**： SiliconFlow 挂掉时重排仍可用（现在会整体降级到 A2）

   如果哪天有 GPU，本地部署才可能同时快又省钱。

5. **量化 / 两级重排**：QINT8 量化模型公开数据约 120ms/50 对（仍是本地 CPU 口径）；
   两级策略（本地小模型粗排 100 条 → API 精排 10 条）在有 GPU 时才划算。

> **这一条是本项目里我改过的一个判断。** 最初写文档时我以为「本地化 = 更快」，
> 查证后发现公开基准恰好相反，所以改成如实写「省钱但不更快」。
> 工具选型里最容易出现的错误就是拿不同硬件口径的数字做比较。
